## 1. 前置问题:支柱 F 的立项动因已经塌了

**引用对照**:

- §5-F 原文:「罐头与冻干——**探索玩家的刚需**」;
- §7.1 决议原文:「**不做腐坏惩罚**,以品质分级替代」。

**冲突**:支柱 F 的完整叙事建立在「食物会坏」上。既然不做腐坏惩罚,那么「罐头延长保质期」「冻干保藏」「防腐剂延长时限」全部失去目标函数——F 的地基当时是空的。不重新定义动因,M2/M3 做出来的罐头线只会是**多一组没人吃的物品**:没有玩家会被"不会坏"说服去多跑两道工序。

### 1.1 重立动因(已定案)

采纳 **1+2+4** 三项,箱式物流作为加分项;~~动因 3「增益的时空转移」~~ **已裁定去除**——理由是它与菜肴 / 中央厨房的核心卖点重叠,且会持续压迫 §2 的数值克制红线。

| 编号 | 动因 | 说明 | 取舍理由 | 风险 |
| --- | --- | --- | --- | --- |
| **1** | **物流密度** | 散装菜肴是不可堆叠的异质物品,占格;罐头统一容器、**堆叠 64**、可装箱打包 | 这是 GT 的原生语言(粉/锭/仓/箱的形态压缩),与任何食物模组都不撞,且能被物流生态自然消费 | 若未安装物流类模组,价值感会打折——因此必须与 2/4 绑定成立 |
| **2** | **第二张食物清单(SoL 多样性平行出口)** | 罐头走**独立 SKU**(每个 SKU 独立物品 id),与本模组 50+ 食品并列计入 SoL 多样性 | 直接放大本模组与 SoL 的核心联动(§7.2);罐头不是"菜肴的再封装",而是另一条产线的终端 | 增加贴图/注册量;§5 决议已放开食品层物品预算 |
| **4** | **自动化收容与产能出口** | 农业末端产出存在水桶效应,需要收纳形态;罐头是可无限扩展的工业出口,保证 EMI 全链闭合 | 给高产期作物一个"不会溢出的池子",符合 §4.1「每样原料都有工业归属」 | 单独成立会变成"为消纳而注册",须与 1/2 绑定 |
| 5 | *(加分项)* 仓储 / 箱式物流红利 | 罐头 → 打包机 → 罐头箱 → 火车 / 箱子 / 仓储流转 | GTCEu 已**自带打包机与大型打包机**,几乎零资产成本(§2) | 依赖下游物流生态;不作为立项理由 |
| ~~3~~ | ~~增益的时空转移~~ | ❌ **已去除** | 与菜肴/中央厨房定位重叠,挤压 §2 数值克制的空间 | — |
| ~~6~~ | ~~保鲜~~ | ❌ 已废 | 与 §7.1 直接冲突 | 任何以"延长保质期"为卖点的设计一律不做 |

### 1.2 动因 3 被去除后的连带说明(重要)

动因 3 去除后,罐头**不得**再被当作"把精制饱足增益带去野外"的通道来推销。但它仍然由机器产出,天然落在 §7.1 的**精制档**里——这套数据关系需要一个明确口径,见 §11-1(仍待定)。当前倾向:**罐头走精制档映射,但不对效果做第三条数值线**,避免又生一套表。

> 📌 **设计公约**:本节的教训适用于未来所有立项——**先立动因,再谈机制**。凡是发现某个内容章节说不清"玩家为什么要它",先补动因,再往下做机制与数值。

### 1.3 由此连锁废弃的设计

| 作废项 | 原出处 | 理由 |
| --- | --- | --- |
| 罐头保质期 / 货架期 | §5-F 隐含 | 无腐坏机制,保质期无对象 |
| 灭菌版 vs 未灭菌版双版本罐头 | §5-F 隐含(高压釜) | 两者差异只能体现在保质期上 → 无对象 |
| 防腐剂用于延长时限 | §5-F、M0 §2.3 | **材料仍建议新增**,但用途改为"部分罐头配方的投入项",不再与时间挂钩(见 §11-3) |

## 3. 罐头容器方案(收口 §10-4)

### 3.1 四个方案定义

| 代号 | 方案 | 形态 |
| --- | --- | --- |
| **A** | 流体容器 | 空罐实现 `IFluidHandlerItem`;为每种罐头内容编一个"内容流体";靠 `CannerLogic` 动态逻辑自动灌装/抽取 |
| **B** | 静态装罐配方 | 罐头为**独立物品 id**;`CANNER_RECIPES` 静态配方:食材 + 空罐 + [封藏介质流体] → 罐头 |
| **C** | 混合 | 半成品/内容物走流体(便于管道运输),成品走静态 |
| **D** | 新增专属配方类型 | 自建 `CANNING_RECIPES` + 专属机器 UI |

### 3.2 评价矩阵

| 评价维度 | A 流体容器 | B 静态配方 | C 混合 | D 专属类型 |
| --- | --- | --- | --- | --- |
| **SoL 多样性计数** | ❌ **致命**:所有罐头只算**同一种**(SoL 按 Item 本体判定,不分 NBT) | ✅ 每 SKU 各计一次 | △ 成品侧 OK | ✅ |
| 物品 / 贴图预算 | △ 省了物品 id,但每种罐头仍要一张贴图 → **实际不省** | ❌ 按已放开的食品层预算执行 | ❌ 最贵 | ❌ |
| EMI / JEI 可读性 | △ 需叠加渲染流体 + 标签,玩家难分辨 | ✅ 一眼看明白 | △ | ✅ 但脱离 GT 生态 |
| 能否表达"固体内容" | ❌ 午餐肉/笋/红烧肉无天然流体表达,需编造内容流体 | ✅ | △ | ✅ |
| 与管道 / 物流 / 机器生态的衔接 | ✅ 天然接入 | △ 需自行接入 | ✅ | ❌ 需自研 UI 与 EMI 绑定 |
| 被动态逻辑遮蔽的风险 | ⚠ 存在(虽静态优先,但某组合一旦无静态配方就会走通用灌装,产出非预期品) | ✅ 无 | ⚠ **最高**(两条路径并存,歧义难查) | ✅ |
| 灌装之外能否被其他机器处理 | ✅ 提取机 / 打包机 / 离心机都能处理 | △ | ✅ | ❌ |
| 实现复杂度 | 高:需自写容器类、`getFoodProperties(stack, entity)`、`finishUsingItem`、流体→效果查表 | **低**:纯 datagen 配方 + 标准 `FoodProperties` | 最高 | 最高 |

### 3.3 已定案:**B 为唯一主体**;不做 C / D;A 仅在内容物本身就是流体时适用

1. **SoL 多样性是本项目的一等公民**(§7.2 决议)。A 方案把所有罐头压成一种计数,等于把候选动因 2 直接砍掉——这是与「食物种类极大拓展」定位相悖的结构性损失,任何实现便利都不值这个价。
2. **首批罐头内容物绝大多数是固体**,A 方案要为"午餐肉""笋罐头"编造流体条目,本质是把物品注册成本换成流体注册成本,预算不降反增(贴图还是一 SKU 一张)。真正的流体内容(高汤、浓缩汁、酱油)本来就走流体层,不需要经过"罐"这个形态。
3. **D 不必要且有害**:装罐机的语义与 UI(`CANNER_OVERLAY` / `CANISTER_OVERLAY` / `DARK_CANISTER_OVERLAY` 槽位覆盖图)已完全贴合装罐;另开类型既破坏 GTCEu 生态一致性,又白白背上 UI 与 EMI 绑定的自研成本。**明确否决**。
4. **C 的歧义风险不值**:两条路径并存时,"内容物流体直接装罐"与"装填静态罐头"会在同一台机器上竞争匹配,排障成本长期存在。

**📌 决议(2026-09-07 批准,§10-4 就此收口)**

- [x] 罐头走 **`CANNER_RECIPES` 静态配方**,**不新增配方类型、不新增装罐专属机器**;
- [x] 每个罐头 SKU = 一个**独立物品 id**、独立营养值,独立计入 SoL 多样性;
- [x] 不引入"内容流体"抽象;内容物天生是流体者(高汤、酱油、浓缩汁)直接在流体层处理,不经由"罐"的形态;
- [x] SKU 设立遵循**合理处理原则**(§5):主料 × 介质组合合理即注册为独立 SKU。

## 4. 容器供应链:空罐从哪来

### 4.1 两条容器线

决议:**不新增 tinplate 材料**(新增材料会连带整套形态与贴图,收益不抵成本),直接用现成的 Tin 板 / 钢板;**封口消耗焊锡**。

| 容器 | 适用 | 已定案产线 | 依据与备注 |
| --- | --- | --- | --- |
| **马口铁空罐** `empty_tin_can` | 肉类 / 蔬菜 / 汤品 / 午餐肉 | ① 成型压机:锡板或钢板 + 非消耗「罐身模具」→ **罐身**<br>② 装罐机 / 组装机:**罐身 + 焊锡(锭或其熔融态)**→ **空罐**(封口) | FORMING_PRESS 支持 6 物品输入与非消耗模具(§2);`soldering_alloy` 已存在且自带 ingot 与液态形态(544K),无需新增材料【src】`FirstDegreeMaterials.java:590-595` |
| **玻璃密封罐** `empty_jar` | 果酱 / 泡菜 / 糖水水果 / 花生酱 | 仅新增**一个物品** `empty_jar`;不另设"密封盖"物品 | 决议以"少加物品"为上;封口语义由装罐配方本身承载,不再体现为独立物品 |

> 💡 **可选 flavor 升级 [草案]**:`soldering_alloy` 配方含铅(Tin6 + Lead3 + Antimony1)。可增设"无铅焊缝"升级路线(不锈钢罐身或改用无铅焊料)作为高阶容器变体。
> 好处:给不锈钢产线一个明确需求位,也贴近真实罐头工业史;
> 代价:多 1 个容器变体 + 1 套贴图。**建议不做**,留进长尾候选池。

### 4.2 回收闭环(推荐)

吃完罐头 **返还空罐 / 空瓶**。1.20.1 下可用 `finishUsingItem` 返回剩余物,或自写 `IRecipeRemainder` 风格组件——与 GTCEu `ItemFluidContainer.getRecipeRemained` 的做法同构。好处:

- 容器从"耗材"变成"流动资产",贴合 GT 的物流与回收语义;
- 给金属板 / 玻璃产线一个持续需求,而不是一次性过路税。

> ⚠ **SoL 判定不受影响**:返还行为发生在 `LivingEntityUseItemEvent.Finish` 之后,SoL 仍按被吃掉的罐头 SKU 计数。

## 5. 装填与变体:流体槽就是我们要的"电路"

装罐机静态配方的物品输入上限只有 **2**,而「食材 + 空罐」已经吃满两个槽位——**没有留给编程电路的位置**。这是个硬约束,但它恰好逼出一个更合适的设计:

> **把封藏介质放到流体槽里,用「介质」而不是「电路」当变体选择器。**

| 封藏介质(流体输入,1 个槽位) | 适用内容 | 语义 | GTCEu 可用性 |
| --- | --- | --- | --- |
| 盐水 / 卤水 | 肉类、蔬菜、笋 | 咸鲜 | 需新增(盐已存在) |
| 糖水 | 水果 | 糖水桃 / 梨 / 橘子 | 需新增(糖已存在) |
| 食用油 | 油浸鱼类(沙丁鱼 / 鲭鱼) | 油浸 | **seed_oil 已存在**(M0 §2.1),零新增材料 |
| 番茄汁 / 茄汁 | 茄汁沙丁鱼、番茄罐头 | 茄汁底 | 需新增 |
| 高汤 | 汤品类罐头 | 浓汤 | 需新增(已在 dishes-and-gains §7-5 待定清单) |

**配方骨架示例**

```
装罐机 / LV   猪肉馅×8 + 空罐×8 + 盐水 1000mB     → 午餐肉罐头×8
装罐机 / MV   番茄丁×8 + 空罐×8 + 番茄汁 500mB    → 番茄罐头×8
装罐机 / MV   鱼片×8   + 空罐×8 + 食用油 1000mB   → 油浸鱼罐头×8
装罐机 / MV   红烧牛肉(烹饪机产出)×8 + 空罐×8 + 生抽 500mB → 红烧牛肉罐头×8
```

- 同一主料 × 不同介质 = 不同 SKU = **各自计入 SoL 多样性**;
- 批量乘数与"非消耗模具"的先例已在药片切片线验证(§2),按批量写法安全;
- 📌 **工艺边界规则**:装罐机只有 2 个物品槽,**装填阶段不接受 3 种以上配料**。需要多配料时先在**通用烹饪机**里合成成品菜肴,再作为单一主料装罐。这条边界正好框定了整条链的形状:烹饪负责"配方组合",装罐负责"封存与密度"。

## 6. 首批罐头 SKU(挂在 M2,随肉品线落地)

命名建议:id 前缀 `gfe:`,形如 `canned_<主料>_<介质>`,中文名走 `<介质><主料>罐头`。

| SKU | 主料来源 | 介质 | 电压 | 落地条件 |
| --- | --- | --- | --- | --- |
| 午餐肉罐头 | 猪肉馅(绞碎形态) | 盐水 | LV | **可最先落地**:只需盐,不依赖新增介质材料 |

## 8. 便当与礼盒 —— **已取消**(存档记录)

**决议(2026-09-07):取消便当与礼盒的设计。** 本节不再作为设计内容,仅保留取消理由,防止后续讨论重复提出。

### 8.1 取消理由

1. **动因不成立**:支柱 F 重立动因后仅剩物流密度、多样性平行清单、产能收容三项(§1.1);"便携组合餐"不在其中。
2. **与 SoL 核心联动相冲**:SoL 统计的是「玩家吃过的 Item 种类数」,把 3 道菜合成 1 个可食用便当 = **计数从 3 变 1**。本项目是以多样性为核心卖点的方向,主动引入一个稀释多样性的自有机制不合逻辑(处置候选 B/C/D 要么实现成本高、要么进一步稀释多样性)。
3. **装罐已经覆盖了它的功能**:罐头堆叠 64 + 装箱运输,已经把"携带多份食物"这件事解决得更干净,且每个 SKU 各自计数。

### 8.2 连带影响(**已回填完成**,2026-09-07)

## 9. 冻干(HV):复用而非新建

| 所选方案 | 说明 | 取舍 |
| --- | --- | --- |
| **已定案:复用真空冷冻机多方块** | GTCEu 已有此多方块,IO 1 物品入 / 1 物品出 / 2 流体入 / 1 流体出,足以表达"冻干 + 升华水回收" | **零机器资产成本**,符合 §2.4「不重复造轮子」;代价是多方块门槛较高、占地大 |
| *(已否)* 新增单方块冷冻干燥机 | 可让冻干更早解锁 | 违反 §2.4,且 GTCEu 没有单方块冷冻机的先例 |
| *(已否)* 新增冻干专用多方块 | 便于做深度(多出成、升华水回收) | 与现有机重合度过高,不推荐 |

**节点:HV**(与真空冷冻机所在 tier 对齐,决议)。若后续发现"升华水 + 多出成"确有深度需求,再评估是否在 IV 增设专用多方块——届时按本文 §1 的原则走重新立项。

同时,冻干的卖点也已随之重定义(原"保鲜"作废,§1.2):**脱水减重 → 堆叠 64 与运输密度更高 → 食用前需复水(烹饪机一步)**。这与动因 1 同源。
